02 / Identity vocabulary

A principal is an identity, not a permission

Tenant

An organization's Microsoft Entra directory. It contains users, application identities, and access configuration.

User principal

The security identity representing a person who signs in.

Service principal

The security identity representing an application or workload in a particular tenant.

Authentication

Prove who the caller is. Entra issues tokens after the appropriate authentication flow.

Authorization

Decide what that caller may do. The resource checks permissions and access policies.

A successful sign-in or token request does not mean the caller may read every document.

Microsoft sources: Application objects and service principals Graph authentication and authorization

03 / Two portal views

App registration vs. enterprise application

App registrations: the blueprint

Manage the application object in its home tenant.

  • Application (client) ID and supported account types.
  • Redirect URIs and confidential-client credentials.
  • API permission requests and exposed scopes or app roles.

Enterprise applications: the local instance

Manage service principals in this tenant.

  • Granted consent and tenant-specific access.
  • User/group assignment and SSO configuration.
  • Sign-in activity and application lifecycle.

For a registered application, these are related objects, not two copies of your code. Registration stores identity configuration; it does not upload or host the app.

Managed identities are another service-principal type and do not have an associated application object. The blueprint analogy here describes application-type service principals.

In a multitenant app, customer consent establishes the local application instance and its granted permissions. Consent in one customer tenant does not grant access in another.

Do not confuse IDs: the client ID identifies the app across tenants; an object ID identifies a specific directory object; the tenant ID identifies the directory.

Illustrative IDs, not real identifiers. A single-tenant app is restricted to its home tenant; multitenant support must be configured and implemented deliberately.

05 / Permission lifecycle

Request, consent, and enforce are different steps

1

Developer requests

Configure the API permissions the application needs. A permission request is not a grant.

2

Tenant consents

A user or authorized administrator approves access, subject to the permission's consent requirements and tenant policy.

3

Resource enforces

The API validates the access token and applies the resource's authorization rules on each call.

App assignment controls who can sign in to the app when assignment is required. It is not a substitute for Graph consent or SharePoint Embedded container membership.

Application management continues after consent: review permissions, manage credentials, monitor sign-ins, and remove obsolete access.

Microsoft sources: Access, consent, assignment, and lifecycle Graph permissions and enforcement

06 / The API bridge

Microsoft Graph is the API, not the identity provider

One REST endpoint for many Microsoft cloud resources, including Entra and SharePoint. Use HTTP directly or an SDK.

Your app

Gets a token from the Microsoft identity platform.

→

Microsoft Graph

Receives the bearer token and authorizes the API request.

→

Resource

Users, groups, documents, or Embedded containers.

GET https://graph.microsoft.com/v1.0/me
Authorization: Bearer <access-token-for-Microsoft-Graph>

This profile example requires delegated access, such as User.Read. /me means the signed-in user and is not an app-only endpoint. The examples in this deck use the public-cloud v1.0 API.

08 / A backend token flow

Client credentials: an app proves its identity

Confidential backend

Uses its client ID and a protected credential.

→

Consuming tenant's Entra

Issues an access token for Microsoft Graph.

→

Microsoft Graph

Checks the token and operation permissions.

POST https://login.microsoftonline.com/{consuming-tenant-id}/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

client_id={app-client-id}&client_secret={protected-secret}
&scope=https://graph.microsoft.com/.default
&grant_type=client_credentials

Conceptual request, not an executable command: URL-encode form values. .default requests the statically configured permissions granted for Graph; it does not mean "all Graph permissions." Certificates or federated credentials avoid shared secrets.

Never put an app credential in browser HTML or JavaScript. An ID token identifies a sign-in; use an access token intended for Graph to call Graph.

09 / Storage behind your own UX

What SharePoint Embedded adds

An API-only file and document platform built on Microsoft 365. Your app supplies the experience; Microsoft 365 supplies document capabilities.

Your app

Business workflows, UI, authentication integration, and Graph calls.

Embedded platform

Containers, files, folders, metadata, versions, and Office collaboration.

Customer tenant

Documents stay in its Microsoft 365 tenant boundary, with supported governance and compliance controls.

Owning the application does not move customer content into the developer's tenant. Container residency and application ownership are different concepts.

Do not assume every advanced capability is included automatically: check the relevant licensing, configuration, and preview requirements before enabling features.

Microsoft sources: Embedded overview and build paths Files, Office, and production requirements Container residency

10 / Embedded object model

Owning app → container type → containers

Owning Entra app

The application that creates and manages the storage family.

One owning app : one type.

→

Container type

Defines app access, behavior, and billing accountability.

Created in the developer tenant.

→

Many containers

Files and folders within a storage/security boundary.

Created in consuming tenants.

Illustrative design: a project-management app owns a "Project documents" type; each project gets a container with its own members.

Three different IDs: app client ID = application; container type ID = storage family; container ID = storage instance and its Graph drive ID.

A container type is a SharePoint Embedded resource, not an Entra application object. Its owning app must register it in every consuming tenant, including when developer and consumer are the same tenant.

11 / The authorization stack

Graph consent is necessary, but not sufficient

1

Graph permission

FileStorageContainer.Selected

Allows the app to call Embedded container/content APIs in the chosen access mode.

2

Container-type grant

Registration grants the app actions such as read, readContent, or writeContent for this type.

Separate delegated and application grant arrays.

3

User's container role

For delegated access: Reader, Writer, Manager, or Owner.

The role limits what this user can do in this container.

Delegated: Graph authorization + intersection of app's type grants and user's container role.
App-only: Graph authorization + app's type grants; no user-membership boundary.

Delegated FileStorageContainer.Selected does not inherently require admin consent, though tenant policy can restrict user consent. Its application variant requires admin consent. Registration has its own admin-consent requirements.

Microsoft source: Permission layers, access modes, consent, and container roles

12 / Setup is not runtime

Register the typeFileStorageContainerTypeReg.SelectedConsuming tenant, owning app only, with admin consent. Delegated registration also requires an authorized admin user.

Only request what that stage needs. Do not distribute owning-tenant type-management permission requests to customer tenants.

Type creation is not supported with app-only access. Container creation is different: it requires a confidential client, even with delegated access. A public SPA/mobile client must route creation through a protected backend.

13 / Customer onboarding

Install the identity, then register the storage family

  1. Establish the owning app's service principal in the consuming tenant and obtain the required admin consent.
  2. As the owning app, acquire a Graph token in that tenant with registration permission.
  3. Register the type and grant only the required delegated/app-only actions.
  4. Validate returned grants; allow up to one hour for permission propagation. Complete applicable billing before use.
PUT https://graph.microsoft.com/v1.0/storage/fileStorage/containerTypeRegistrations/{containerTypeId}
Authorization: Bearer <owning-app-token-for-consuming-tenant>
Content-Type: application/json

{"applicationPermissionGrants": [{
  "appId": "{owning-app-client-id}",
  "delegatedPermissions": ["none"],
  "applicationPermissions": ["create", "read", "write", "readContent", "writeContent"]
}]}

Illustrative app-only grants matching this repository's trial workload; not a universal production profile. writeContent requires readContent. Other applications can receive specific type grants too; a "guest app" is not a guest user.

PUT replaces the complete registration. Preserve existing apps/grants intentionally; a targeted PATCH uses the registration's current etag.

Microsoft source: Consent, registration payloads, replacement, and propagation

14 / From setup to documents

Use Embedded containers, then familiar DriveItems

# Create a container from a confidential backend
POST https://graph.microsoft.com/v1.0/storage/fileStorage/containers
{"displayName": "Project Alpha", "containerTypeId": "{containerTypeId}"}

# List files and folders in its root
GET https://graph.microsoft.com/v1.0/drives/{containerId}/root/children

# Upload or replace a small file
PUT https://graph.microsoft.com/v1.0/drives/{containerId}/root:/brief.txt:/content
<file bytes>

Abbreviated HTTP examples: supply a Graph bearer token and the appropriate content type. Each operation needs its matching type grant; delegated calls also need user access. The container ID is the drive ID; returned file IDs are DriveItem IDs.

User-facing production app

Prefer delegated access so actions reflect the user and are constrained by container roles.

This repository's trial app

A confidential, app-only backend with no user sign-in. Keep it private and use test data; UI users all act as the same application.

15 / Billing is a separate layer

Choose who pays before creating the type

Trial

trial

No Azure billing profile. Developer and consumer are the same tenant.

30 days; up to 5 containers including recycled containers; 1 GB per container.

Standard billing

standard

The developer/owning tenant pays for usage, including usage in customer tenants.

Often internal apps or an ISV that absorbs or recovers costs separately.

Pass-through billing

directToCustomer

Each consuming tenant pays for its usage through its Azure subscription.

Customer billing onboarding is required.

A type cannot change its billing model, and a trial cannot convert to production. Plan a new type and storage transition rather than treating this as a toggle.

Single-/multitenant app design and billing model are separate decisions. An ISV can use standard billing; multitenant does not automatically mean customer-paid.

Microsoft sources: Billing models and permanence Classifications and trial limits

16 / Developer-paid configuration

Standard: attach billing in the owning tenant

Prerequisites

  • SharePoint tenant, Azure subscription, and resource group in the developer tenant.
  • Container type owner, or SharePoint Embedded Administrator / Global Administrator.
  • The configuring person also needs Azure subscription Owner or Contributor access.

Guided setup

  1. Create the type with standard billing.
  2. In the SharePoint Embedded VS Code extension, select the type and Attach billing.
  3. Select the approved Azure subscription and resource group.
  4. Validate billing, then register the type in each consuming tenant.
# Alternative: authorized administrator, SharePoint Online Management Shell
Add-SPOContainerTypeBilling -ContainerTypeId <type-id> `
  -AzureSubscriptionId <subscription-id> -ResourceGroup <group> -Region <region>

Entra admin authority and Azure subscription RBAC are separate. Admin consent does not confer billing-resource access.

The command is a configuration illustration, not run by this deck; PowerShell tooling is not included in this repository's trial devcontainer.

Microsoft source: Standard billing roles, Attach billing, and PowerShell

17 / Customer-paid configuration

Pass-through: the customer activates billing

Create a directToCustomer type and register it in the consuming tenant. Do not attach developer-tenant billing for this model.

Customer prerequisites

Billing Administrator or Global Administrator in the consuming tenant, plus Owner or Contributor on its Azure subscription and an available resource group.

The SharePoint Embedded Administrator role alone is insufficient for this billing procedure.

Microsoft 365 admin center path

Setup → Files and Content → Automate Content with Microsoft Syntex → Go to Syntex settings → Apps → SharePoint Embedded

Turn on the service, choose subscription/resource group, review, and save.

Before initial use, valid customer billing is required. Verify the linked subscription, app status under SharePoint Embedded > Apps, and pilot access.

Portal labels can change; use the linked procedure. Turning off Embedded or disconnecting a previously linked subscription blocks new container creation; existing containers/content remain accessible. It is not a reliable "revoke all access" mechanism.

19 / Put the layers together

Example: can a project user edit a file?

Illustrative delegated-access scenario: the app has FileStorageContainer.Selected, its type grants allow content writes, and customer billing is valid.

User is a Reader

The app can request a write, but the user's container role does not permit it.

Result: the edit is not authorized.

User is a Writer

The app's type grants and the user's role permit content edits, assuming the other resource policies allow the operation.

Result: the edit can be authorized.

If the same backend uses an app-only token, these user roles no longer constrain it. The app must not present app-only access as user-scoped authorization.

20 / The implementation map

Four questions to carry into the build

Who is calling?

Register the app; distinguish its blueprint from the service principal in each tenant. Choose delegated or app-only authentication deliberately.

What may it do?

Request and consent the right Graph permissions. Register type grants; for delegated operations, assign the user's container role.

Where are the documents?

Create the type in the owning tenant and containers in consuming tenants. Work with content through Graph DriveItems.

Who pays?

Choose trial, developer-paid, or customer-paid at type creation. Attach/activate Azure billing and monitor the actual meters.

Build order: Entra app → container type → standard billing (if applicable) → customer consent + registration → pass-through billing (if applicable) → containers → files.

Use the repository README for the private, app-only trial. Use Microsoft's end-to-end journey for production and customer onboarding.
